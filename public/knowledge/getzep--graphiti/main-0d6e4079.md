## 1. 项目定位

README 将 Graphiti 定位为“为 AI Agent 构建和查询时序上下文图（temporal context graphs）的框架”，并强调它不是静态知识图谱：事实带有有效期，保留到源数据的溯源，支持预设与学习到的本体（[README.md@72b5c59](https://github.com/getzep/graphiti/blob/72b5c59c06607e09ea855be61b6ff5a3446fc951/README.md)）。

README 给出的 context graph 组成包括：

| 组成 | README 描述 |
|---|---|
| Entities / nodes | 人物、产品、策略、概念，摘要可随时间演化 |
| Facts / Relationships / edges | 实体到实体的三元组，带时间有效期 |
| Episodes | 原始摄入数据，作为溯源地 |
| Custom Types / ontology | 通过 Pydantic 模型定义实体和边类型 |

以上来自 [README.md@72b5c59](https://github.com/getzep/graphiti/blob/72b5c59c06607e09ea855be61b6ff5a3446fc951/README.md)。

README 还明确区分 Graphiti 与 Zep：Graphiti 是开源框架，使用者自带图数据库、LLM 和 embedder，并自行构建摄入、租户、访问控制和运维；Zep 是托管/治理的上下文层，Graphiti 是 Zep 内部的图构建框架（[README.md@72b5c59](https://github.com/getzep/graphiti/blob/72b5c59c06607e09ea855be61b6ff5a3446fc951/README.md)）。README 同时声明两者都不是“agent memory product”：Graphiti 是建图框架，Zep 统一并服务企业上下文（[README.md@72b5c59](https://github.com/getzep/graphiti/blob/72b5c59c06607e09ea855be61b6ff5a3446fc951/README.md)）。

### 2.3 后端抽象：按 `GraphProvider` 生成查询

`graph_queries.py` 的模块 docstring 说明它提供面向 Neo4j 和 FalkorDB 的数据库无关查询生成，覆盖索引创建、全文搜索和批量操作（[graph_queries.py@72b5c59](https://github.com/getzep/graphiti/blob/72b5c59c06607e09ea855be61b6ff5a3446fc951/graphiti_core/graph_queries.py)）。代码中：

- `get_range_indices` 对 `FALKORDB`、`KUZU` 和默认分支返回不同索引语句；默认分支是 Neo4j 风格 `IF NOT EXISTS` 语法（[graph_queries.py@72b5c59](https://github.com/getzep/graphiti/blob/72b5c59c06607e09ea855be61b6ff5a3446fc951/graphiti_core/graph_queries.py)）。
- `get_fulltext_indices` 对 FalkorDB 拼接 stopwords，对 Kuzu 使用 `CREATE_FTS_INDEX`，默认使用 Neo4j 全文索引（[graph_queries.py@72b5c59](https://github.com/getzep/graphiti/blob/72b5c59c06607e09ea855be61b6ff5a3446fc951/graphiti_core/graph_queries.py)）。
- `get_nodes_query` 通过 `NEO4J_TO_FALKORDB_MAPPING` 和 `INDEX_TO_LABEL_KUZU_MAPPING` 将全文索引名映射到后端标签（[graph_queries.py@72b5c59](https://github.com/getzep/graphiti/blob/72b5c59c06607e09ea855be61b6ff5a3446fc951/graphiti_core/graph_queries.py)）。
- `get_vector_cosine_func_query` 分别返回 FalkorDB 的 `(2 - vec.cosineDistance(...))/2`、Kuzu 的 `array_cosine_similarity(...)`、默认的 `vector.similarity.cosine(...)`（[graph_queries.py@72b5c59](https://github.com/getzep/graphiti/blob/72b5c59c06607e09ea855be61b6ff5a3446fc951/graphiti_core/graph_queries.py)）。

### 2.4 Prompt / LLM 路由

`GraphitiClients.complete_prompt` 的 docstring 描述了两种路径：无 runtime 时走 legacy 路径，即 builder → `ChatPrompt.as_messages` → `llm_client.generate_response`；有 runtime 时走 `LLMRuntime.complete`。docstring 还说明 schema 来自不可变的内置注册表，而不是用户 library（[graphiti_types.py@72b5c59](https://github.com/getzep/graphiti/blob/72b5c59c06607e09ea855be61b6ff5a3446fc951/graphiti_core/graphiti_types.py)）。

`uses_prompt_routing` 只有在 `clients` 是 `GraphitiClients` 且 `llm_runtime` 或 `prompt_library` 非空时返回真（[graphiti_types.py@72b5c59](https://github.com/getzep/graphiti/blob/72b5c59c06607e09ea855be61b6ff5a3446fc951/graphiti_core/graphiti_types.py)）。

`resolve_prompt_messages` 的分支是：

1. `clients.llm_runtime` 存在：`resolve_model` → `resolve_builder` → `as_messages`；
2. 否则 `clients.prompt_library` 存在：`get_prompt_builder` → `as_messages`；
3. 否则调用传入的 `legacy_prompt(context)`。

来源：[graphiti_types.py@72b5c59](https://github.com/getzep/graphiti/blob/72b5c59c06607e09ea855be61b6ff5a3446fc951/graphiti_core/graphiti_types.py)。

### 2.6 Saga 摘要选择

`graphiti.py` 中定义了一组 Saga 摘要常量：单次 episode 最大 100,000 字符、最大 prompt 128 KiB、最多 20 个 episode、rebuild batch 10、最大输出 token 8192（[graphiti.py@72b5c59](https://github.com/getzep/graphiti/blob/72b5c59c06607e09ea855be61b6ff5a3446fc951/graphiti_core/graphiti.py)）。

`select_saga_summary_episodes` 的行为可直接从代码读出：

- 按输入顺序从旧到新装入 episode，累计字符不超过 `max_episode_chars`；
- 若第一条就超限，则截断该条而不是跳过；
- 若已有选中条目后下一条放不下，则停止并标记 `dropped=True`，后续 episode 推迟；
- 返回值包含选中的 `(content, valid_at, created_at)` 列表、选中内容的 UTF-8 字节数、以及是否 dropped。

来源：[graphiti.py@72b5c59](https://github.com/getzep/graphiti/blob/72b5c59c06607e09ea855be61b6ff5a3446fc951/graphiti_core/graphiti.py)。

## 4. 设计取舍

以下条目中，直接来自代码/文档的为事实；“取舍评价”属于基于代码形态的推断。

1. **后端可移植性 vs 查询字符串分支维护**  
   `graph_queries.py` 将不同后端的索引、全文查询和向量函数集中到一组函数中，并通过 provider 条件分支选择语法（[graph_queries.py@72b5c59](https://github.com/getzep/graphiti/blob/72b5c59c06607e09ea855be61b6ff5a3446fc951/graphiti_core/graph_queries.py)）。【推断】优点是查询生成集中、调用方不直接写后端语法；代价是多个函数内重复 provider 分支，索引名映射也增加维护面。

2. **Prompt 扩展性 vs 多路径一致性**  
   代码同时保留 legacy prompt、prompt library 和 LLM runtime 路径；`uses_prompt_routing` 决定是否进入客户端路由（[graphiti_types.py@72b5c59](https://github.com/getzep/graphiti/blob/72b5c59c06607e09ea855be61b6ff5a3446fc951/graphiti_core/graphiti_types.py)）。【推断】取舍是兼容旧调用并允许自定义 prompt/runtime，但三条路径需要行为对齐和测试覆盖。

3. **时序语义 vs 实现复杂度**  
   README 强调事实有效期、失效不删除和溯源到 episodes（[README.md@72b5c59](https://github.com/getzep/graphiti/blob/72b5c59c06607e09ea855be61b6ff5a3446fc951/README.md)）；索引定义中确实出现 `valid_at`、`invalid_at`、`expired_at`（[graph_queries.py@72b5c59](https://github.com/getzep/graphiti/blob/72b5c59c06607e09ea855be61b6ff5a3446fc951/graphiti_core/graph_queries.py)）。【推断】这要求写入和查询都处理时间窗口；但失效判定与历史查询实现未读，不能确认其复杂度控制方式。

4. **Saga 摘要的上下文预算**  
   `select_saga_summary_episodes` 用字符预算从旧到新打包，单条超限时截断，后续 episode 推迟（[graphiti.py@72b5c59](https://github.com/getzep/graphiti/blob/72b5c59c06607e09ea855be61b6ff5a3446fc951/graphiti_core/graphiti.py)）。【推断】取舍是保证增量摘要能沿时间推进，同时避免 prompt 超限；代价是可能截断超长单条或延迟后续内容。

5. **客户端容器的类型化边界**  
   `GraphitiClients` 是 Pydantic 模型，但将驱动、LLM、embedder 等异构对象放在一起，并启用 `arbitrary_types_allowed`（[graphiti_types.py@72b5c59](https://github.com/getzep/graphiti/blob/72b5c59c06607e09ea855be61b6ff5a3446fc951/graphiti_core/graphiti_types.py)）。【推断】优点是客户端依赖集中、便于传递；代价是这些任意类型对象本身不被 Pydantic 深度校验。

6. **框架边界：自带基础设施 vs 托管平台**  
   README 明确 Graphiti 让使用者自带图数据库、LLM 和 embedder，并自行实现摄入、租户和运维；Zep 提供统一治理和服务（[README.md@72b5c59](https://github.com/getzep/graphiti/blob/72b5c59c06607e09ea855be61b6ff5a3446fc951/README.md)）。【推断】取舍是灵活性和可控性 vs 运维负担与开箱即用程度。

7. **依赖可选化**  
   `pyproject.toml` 将核心依赖与多种可选后端/模型依赖分开，如 anthropic、groq、google-genai、falkordb、kuzu、neptune、tracing 等（[pyproject.toml@72b5c59](https://github.com/getzep/graphiti/blob/72b5c59c06607e09ea855be61b6ff5a3446fc951/pyproject.toml)）。【推断】这是为了减少核心安装负担，同时保留多后端和多模型生态；具体安装组合未在片段中验证。
