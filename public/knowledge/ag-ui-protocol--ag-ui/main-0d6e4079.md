## 1. 项目定位

README 自述 AG-UI 是“开放、轻量、基于事件的协议”，用于把 AI Agent 连接到面向用户的应用；Agent 后端在执行过程中发出与 AG-UI 标准事件类型兼容的事件，并接受少量 AG-UI 兼容输入；协议自带中间件层以适配任意事件传输（SSE、WebSocket、webhook 等），并附带参考 HTTP 实现与默认连接器。来源：[README.md](https://github.com/ag-ui-protocol/ag-ui/blob/7e7c1109f26e77cc32d87d351fb9e0b0bf56ff7f/README.md)。

README 将 AG-UI 放在与 MCP、A2A 互补的位置：MCP 给 Agent 工具，A2A 让 Agent 之间通信，AG-UI 把 Agent 带进用户界面；列出的能力包括流式聊天、双向状态同步、生成式 UI/结构化消息、实时上下文、前端工具集成、human-in-the-loop。来源同上。

**观察到的定位细节**：README 称“约 16 种标准事件类型”（"~16 standard event types"），但同一提交的 proto 生成文件里 `EventType` 已枚举到 31 个具体成员（0–30）加 `UNRECOGNIZED = -1`，涵盖 reasoning、subagent、activity、chunk 等类别。这说明 README 的“约 16”是概览性表述，实际协议面更宽；二者不矛盾，但读代码应以枚举为准。来源：[README.md](https://github.com/ag-ui-protocol/ag-ui/blob/7e7c1109f26e77cc32d87d351fb9e0b0bf56ff7f/README.md)、[generated/events.ts](https://github.com/ag-ui-protocol/ag-ui/blob/7e7c1109f26e77cc32d87d351fb9e0b0bf56ff7f/sdks/typescript/packages/proto/src/generated/events.ts)。

## 3. 基于已读代码的架构

### 3.1 仓库形态：Nx + pnpm 的多包工作区

根 `package.json` 为 `"private": true`，包名 `ag-ui`，使用 `nx`（`^22.4.5`）作为任务编排、`pnpm@10.33.4` 作为包管理器、TypeScript `5.8.2`、Node `>=18`。脚本按目录域拆分：`dev` 关注 `sdks/**`，`dev:integrations` 关注 `integrations/**`，`dev:middlewares` 关注 `middlewares/**`，`dev:examples` 跑 `apps/**`；发布脚本只面向 `./sdks/typescript/packages/*` 与 `./integrations/*`。来源：[package.json](https://github.com/ag-ui-protocol/ag-ui/blob/7e7c1109f26e77cc32d87d351fb9e0b0bf56ff7f/package.json)。

由此可确认的目录职责（有脚本或路径为证）：
- `sdks/typescript/packages/*`：TypeScript SDK 的可发布包集合；
- `integrations/*`：框架集成，独立构建/发布；
- `middlewares/*`：中间件，独立 watch；
- `apps/*`：示例/应用。

索引另列出 `spec/`、`docs/`、`scripts/`、`patches/`、`skills/`、`.claude/`、`.github/` 等目录存在，但本文**未读取其内容**。

### 3.2 分层：协议类型（core）— 线格式（proto）— 客户端运行时（client）

已读片段支持一个三层视图（层次划分属于我的归纳，依据是三个包的导入关系）：

1. **`@ag-ui/core`**：提供事件类型、Zod schema、事件工厂。`event-factories.ts` 从 `./generated/types` 引入 `EventType` 与各事件 TS 类型，从 `./generated/schemas` 引入各 `XxxEventSchema`，从 `./compat` 引入 `XxxEventProps`。来源：[event-factories.ts](https://github.com/ag-ui-protocol/ag-ui/blob/7e7c1109f26e77cc32d87d351fb9e0b0bf56ff7f/sdks/typescript/packages/core/src/event-factories.ts)。
2. **`@ag-ui/proto`**：由 `protoc-gen-ts_proto v2.7.7` / `protoc v7.35.1` 从 `events.proto` 生成，`protobufPackage = "ag_ui"`，依赖 `@bufbuild/protobuf/wire`。来源：[generated/events.ts](https://github.com/ag-ui-protocol/ag-ui/blob/7e7c1109f26e77cc32d87d351fb9e0b0bf56ff7f/sdks/typescript/packages/proto/src/generated/events.ts)。
3. **`@ag-ui/client`**：`AbstractAgent` 抽象基类，从 `@ag-ui/core` 取 `Message`、`State`、`RunAgentInput`、`BaseEvent`、`AgentCapabilities`、`Interrupt`、`PROTOCOL_VERSION`，并用 RxJS 组织运行管道。来源：[agent.ts](https://github.com/ag-ui-protocol/ag-ui/blob/7e7c1109f26e77cc32d87d351fb9e0b0bf56ff7f/sdks/typescript/packages/client/src/agent/agent.ts)。

> **推断**：proto 包是“线格式/编码表示”，core 包是“JSON/TypeScript 表示”。依据是 proto 的事件接口把公共字段收进 `baseEvent` 子消息（`baseEvent: BaseEvent | undefined`），而 core 的事件类型由 Zod schema 生成并直接带 `type`；两者字段语义一致但结构不同。**未读 core 的 `generated/types.ts` / `generated/schemas.ts`，因此该映射关系未验证。**

### 3.3 事件模型：31 个类型 + 组合式 BaseEvent

`generated/events.ts` 的 `EventType` 完整枚举（0–30）为：`TEXT_MESSAGE_START`、`TEXT_MESSAGE_CONTENT`、`TEXT_MESSAGE_END`、`TOOL_CALL_START`、`TOOL_CALL_ARGS`、`TOOL_CALL_END`、`STATE_SNAPSHOT`、`STATE_DELTA`、`MESSAGES_SNAPSHOT`、`RAW`、`CUSTOM`、`RUN_STARTED`、`RUN_FINISHED`、`RUN_ERROR`、`STEP_STARTED`、`STEP_FINISHED`、`SUBAGENT_STARTED`、`SUBAGENT_FINISHED`、`SUBAGENT_ERROR`、`TEXT_MESSAGE_CHUNK`、`TOOL_CALL_CHUNK`、`TOOL_CALL_RESULT`、`ACTIVITY_SNAPSHOT`、`ACTIVITY_DELTA`、`REASONING_START`、`REASONING_MESSAGE_START`、`REASONING_MESSAGE_CONTENT`、`REASONING_MESSAGE_END`、`REASONING_MESSAGE_CHUNK`、`REASONING_END`、`REASONING_ENCRYPTED_VALUE`，另有 `UNRECOGNIZED = -1`。来源：[generated/events.ts](https://github.com/ag-ui-protocol/ag-ui/blob/7e7c1109f26e77cc32d87d351fb9e0b0bf56ff7f/sdks/typescript/packages/proto/src/generated/events.ts)。

`BaseEvent` 携带 `type`、可选 `timestamp`、可选 `rawEvent`、可选 `metadata`。注释明确设计意图：公共字段“组合进每个事件定义而不是重复”，改一处即可影响所有事件；`timestamp` 刻意不用浮点，限制在 JSON 数字可往返的范围内，单位不做规范约束（实践中各 SDK 用 Unix 毫秒），协议本身不对它做计算。来源同上。

事件语义要点（均出自同一文件的注释）：
- `TextMessageStartEvent`：`messageId` 串联后续 content/end；`role` 缺省表示 assistant，该含义由规范散文规定而非 validator 默认值；`name`、`subagentRunId` 可选。
- `TextMessageContentEvent.delta`：允许空字符串，因为提供方会用空增量做 keep-alive，拒绝会杀死正常运行的 run。
- `TextMessageChunkEvent` / `ToolCallChunkEvent`：所有字段可选，作为 start/content/end（或 start/args/end）序列的简写；无字段的 chunk 续接哪个消息属于规范中的“序列问题”。
- `ToolCallArgsEvent.delta`：故意是字符串而非已解析 JSON，因为片段本身不是完整文档。
- `ToolCallResultEvent`：铸造一条新的 tool 消息（因此有自己的 `messageId`），`content` 与 `contentParts` 并存，结构化数据序列化为文本、媒体作为独立 part。
- `StateSnapshotEvent`：整体替换 Agent 状态，用于 delta 无法表达或需要重新同步时。

### 3.4 core 包的模块边界：zod 可选化的“结构性”约束

`event-factories.ts` 的头注释给出一个明确且可检查的设计约束：该模块**运行时依赖 zod**（从 `./generated/schemas` 做值导入，逐个 `schema.parse`），因此**绝不能**从 `src/index.ts` 直接或间接再导出；主入口的契约是“导入 `@ag-ui/core` 运行时不会拉入 zod”，这才使 zod 能作为**可选 peer 依赖**。注释还说明：目前没有任何地方再导出该模块，测试用相对路径导入；若将来要给公开入口，应是 `@ag-ui/core/schemas` 子路径；`src/__tests__/main-entry-zod-free.test.ts` 通过把 `src/index.ts` 打包、将 zod 标为 external、检查产物中是否残留 `zod` 导入来做结构性守护，从而捕获“三层深的再导出”。来源：[event-factories.ts](https://github.com/ag-ui-protocol/ag-ui/blob/7e7c1109f26e77cc32d87d351fb9e0b0bf56ff7f/sdks/typescript/packages/core/src/event-factories.ts)。**这是注释陈述，本文未运行该测试。**

工厂实现统一走一个泛型 `buildEvent(eventType, schema, props)`：把 `type` 与 props 合并后交给 `schema.parse`，返回值类型为 `z.infer<Schema>`。也就是说工厂在构造期做校验，而不是在消费期。已读到的工厂包括：文本消息四件套、工具调用五件套（含 `createToolCallResultEvent`）、`StateSnapshot`/`StateDelta`、`MessagesSnapshot`、`ActivitySnapshot`/`ActivityDelta`、`createRawEvent`、`createCustomEvent`、`createRunStartedEvent`、`createRunFinishedEvent` 及三个 outcome 便捷函数、`createRunErrorEvent`（片段在此截断）。来源同上。

`RUN_FINISHED` 的 `outcome` 设计：可选（省略即 legacy/向后兼容），或显式 `{type:"success"}`、`{type:"interrupt", interrupts}`、`{type:"cancelled"}`；`createRunFinishedSuccessEvent` 额外接受 `pendingToolCallIds`（前端工具调用在本次 run 中没有 `TOOL_CALL_RESULT` 的 id 列表）；`createRunFinishedCancelledEvent` 显式**不接受** `result`，因为被取消的 run 没有返回值，但停止前累积的 `usage` 仍可上报。来源同上。

### 3.5 client 运行时：AbstractAgent 的结构

`agent.ts` 片段定义了 `RunAgentResult`（`result: any` + `newMessages: Message[]`，注释说明收紧为 `unknown` 是破坏性变更，留待 API 决策）与抽象类 `AbstractAgent`。可从字段和 getter 确认的状态：
- `agentId?`、`description`、`messages`、`state`、`subscribers: AgentSubscriber[]`、`isRunning`、`pendingInterrupts: Interrupt[]`（最近一次以 `outcome.type === "interrupt"` 结束时填充，后续成功 run 清除）、`protected middlewares: Middleware[]`。
- `threadId` 访问器**懒生成** UUID：注释说明 Cloudflare workerd 禁止在全局作用域求值期做 crypto 随机，急切 UUID 会让在模块顶层构造 agent 的 Worker 崩溃（引用 issue #3197）。
- `activeRunDetach$?: Subject<void>` 与 `activeRunCompletionPromise`：用于立即脱离当前 run（停止处理其流）。
- `debug` / `debugLogger`：`debug` setter 经 `resolveAgentDebugConfig` 归一化并重建 logger；`debugLogger` 支持 `boolean` 简写。
- `maxEnforcedEntries`：经 `resolveMaxEntries` 归一化。

来源：[agent.ts](https://github.com/ag-ui-protocol/ag-ui/blob/7e7c1109f26e77cc32d87d351fb9e0b0bf56ff7f/sdks/typescript/packages/client/src/agent/agent.ts)。

### 3.6 版本协商：`PROTOCOL_VERSION` 与 peer ceiling

- `PROTOCOL_VERSION` 从 `@ag-ui/core` 导入，注释称它“由 schema 的 `$id` 生成，而不是写在旁边”。
- `compareDeclaredProtocol(declared, spoken)` 返回 `"newer" | "not-newer" | "uninterpretable"`：先用 `/^\d+\.\d+$/` 严格校验两段数字语法，再做 `compareVersions`。注释解释为什么必须先校验：`compareVersions` 会把 `"1"`、`"1.0.0"`、`"1.x"` 都读成等于 `"1.0"`，而规范要求语法外的值按“更新”处理，不能静默接受。
- `warnOnProducerDeclaration` 仅在 `RUN_STARTED` 携带的 `protocolVersion` 与本地不同且不可解释/更新时 `console.warn`；更旧或缺失则静默（“downgrade signal 应被消费者安静地注意到”）。
- `maxProtocolVersion` 是“对端所说的上限”，与“本 SDK 实现的协议版本”（`PROTOCOL_VERSION`）区分；`maxVersion` 是同一值的弃用别名，每进程只警告一次。
- `resolvePeerCeiling` 通过属性描述符沿原型链查找子类是否覆盖 `maxVersion` / `maxProtocolVersion`，避免执行公开 getter 造成递归，并用 `resolvingPeerCeiling` 重入标志兜底。
- 构造期 `resolvedCeilingDuringConstruction()` 校验 ceiling 是 `compareVersions` 能读的字符串，否则抛 `AGUIError`，并提示“从实例字段读的 ceiling 此时还不可用，请从 getter 返回字面量”——这是类字段初始化顺序问题的显式防御。

来源：[agent.ts](https://github.com/ag-ui-protocol/ag-ui/blob/7e7c1109f26e77cc32d87d351fb9e0b0bf56ff7f/sdks/typescript/packages/client/src/agent/agent.ts)。

### 3.7 中断与恢复的语义线索

- `runInputs = new WeakSet<RunAgentInput>()`：只有 `runAgent()` 的输入会被登记，`onInitialize()` 据此判断“恢复答案”是否针对待处理中断；`connectAgent()` 等其他调用只读历史、不回答任何问题，因此被中断的线程仍必须能 connect。注释还说明检查放在 `onInitialize()` 内，是因为子类会在调用 `super` 前先对 pending interrupts 做协调；用模块级 WeakSet 而非实例字段，是因为 `clone()` 跳过字段初始化器。
- `isInterruptExpired` 从 `@/interrupts` 导入，说明存在中断过期判定（实现未读）。
- `keepToolResultsWithCalls` 从 `@/apply/default` 导入，暗示应用事件时会处理“保留有对应调用的工具结果”这类边界。

来源：[agent.ts](https://github.com/ag-ui-protocol/ag-ui/blob/7e7c1109f26e77cc32d87d351fb9e0b0bf56ff7f/sdks/typescript/packages/client/src/agent/agent.ts)。**具体过期规则与保留规则未读，属未覆盖区域。**

### 4.1 事件构造链（已读代码直接支持）

```
createXxxEvent(props: XxxEventProps)
  └─ buildEvent(EventType.XXX, XxxEventSchema, props)
       └─ schema.parse({ type: EventType.XXX, ...props })
            └─ 返回 z.infer<Schema>，即 XxxEvent
```

证据：`buildEvent` 的定义与各工厂的一行委托体。来源：[event-factories.ts](https://github.com/ag-ui-protocol/ag-ui/blob/7e7c1109f26e77cc32d87d351fb9e0b0bf56ff7f/sdks/typescript/packages/core/src/event-factories.ts)。
**含义（推断）**：非法事件在“生产侧构造时”即抛错，而不是等到消费侧；校验规则完全由 `generated/schemas` 决定，本文未读该文件。

### 4.2 客户端运行管道（**推断**，依据 import 与字段）

`agent.ts` 片段在导入区集中引入了这些模块，且引入 RxJS 的 `pipe / Observable / from / of / EMPTY / Subject / defer / concatWith / throwError / lastValueFrom` 与 `catchError / map / tap / finalize / takeUntil`：

```
runAgent(input)
  ├─ onInitialize()                      // 校验 resume 答案 vs pendingInterrupts（runInputs WeakSet 门控）
  ├─ verifyEvents                        // @/verify
  ├─ transformChunks                     // @/chunks：chunk 事件 → start/content/end 序列
  ├─ enforceEvents (+ resolveMaxEntries) // @/enforce：上限/规范化
  ├─ compatibilityBoundaryOperator       // @/middleware/compatibility-boundary
  ├─ defaultApplyEvents                  // @/apply/default：把事件应用到 messages/state
  ├─ convertToLegacyEvents               // @/legacy/convert：旧协议事件适配
  ├─ runSubscribersWithMutation          // ./subscriber：通知订阅者并合并状态变更
  └─ takeUntil(activeRunDetach$) / finalize(...)
```

上述顺序是我根据模块命名与 RxJS 操作符推断的**典型管道顺序**，片段中并未出现 `runAgent` 方法体，因此**顺序与是否全部串联均未验证**。可确证的事实仅是：这些模块被 `agent.ts` 导入，且 RxJS 操作符被导入，说明 run 以 Observable 流组织。来源：[agent.ts](https://github.com/ag-ui-protocol/ag-ui/blob/7e7c1109f26e77cc32d87d351fb9e0b0bf56ff7f/sdks/typescript/packages/client/src/agent/agent.ts)。

### 4.3 一次文本回复的事件序列（协议层，已读类型定义支持）

```
RUN_STARTED (可带 protocolVersion)
  → TEXT_MESSAGE_START { messageId, role? }
  → TEXT_MESSAGE_CONTENT { messageId, delta } *  // delta 可为 ""
  → TEXT_MESSAGE_END { messageId }
  → RUN_FINISHED { outcome?: success | interrupt | cancelled }
```

或由生产者用 `TEXT_MESSAGE_CHUNK` 简写替代中间三事件（字段全可选，缺字段表示“续接已打开的消息”）。工具调用对应 `TOOL_CALL_START → TOOL_CALL_ARGS* → TOOL_CALL_END →（执行后）TOOL_CALL_RESULT`，状态同步对应 `STATE_SNAPSHOT` / `STATE_DELTA`。来源：[generated/events.ts](https://github.com/ag-ui-protocol/ag-ui/blob/7e7c1109f26e77cc32d87d351fb9e0b0bf56ff7f/sdks/typescript/packages/proto/src/generated/events.ts)、[event-factories.ts](https://github.com/ag-ui-protocol/ag-ui/blob/7e7c1109f26e77cc32d87d351fb9e0b0bf56ff7f/sdks/typescript/packages/core/src/event-factories.ts)。`transformChunks` 的存在（导入名）与“chunk 简写”语义相互印证，但转换实现未读。

### 4.4 中断生命周期（**部分推断**）

```
RUN_FINISHED{outcome:{type:"interrupt", interrupts}} → pendingInterrupts = interrupts
下一次 run 成功完成 → pendingInterrupts 清空
runAgent 的 resume 答案 → onInitialize() 对照 pendingInterrupts 校验
isInterruptExpired(...) → 过期中断的处理（规则未读）
```

前半段由 `pendingInterrupts` 字段注释与 `ARUN_FINISHED` outcome 类型直接支持；`isInterruptExpired` 的具体判定与过期后的降级行为**未读**。来源：[agent.ts](https://github.com/ag-ui-protocol/ag-ui/blob/7e7c1109f26e77cc32d87d351fb9e0b0bf56ff7f/sdks/typescript/packages/client/src/agent/agent.ts)、[event-factories.ts](https://github.com/ag-ui-protocol/ag-ui/blob/7e7c1109f26e77cc32d87d351fb9e0b0bf56ff7f/sdks/typescript/packages/core/src/event-factories.ts)。

## 5. 设计取舍

| 取舍 | 证据 | 代价 / 备注 |
| --- | --- | --- |
| 事件用“组合 BaseEvent + 每事件窄化 type”而非继承重复字段 | [generated/events.ts](https://github.com/ag-ui-protocol/ag-ui/blob/7e7c1109f26e77cc32d87d351fb9e0b0bf56ff7f/sdks/typescript/packages/proto/src/generated/events.ts) 中 `BaseEvent` 注释 | 线格式多一层 `baseEvent` 子消息，JSON 侧是否扁平未验证 |
| chunk 事件把 start/content/end 三事件压成一个、字段全可选 | 同文件 `TextMessageChunkEvent` / `ToolCallChunkEvent` 注释 | 语义依赖“序列”而非单事件自描述，消费方必须维护打开中的消息/调用状态 |
| 工厂在构造期用 zod 校验 | [event-factories.ts](https://github.com/ag-ui-protocol/ag-ui/blob/7e7c1109f26e77cc32d87d351fb9e0b0bf56ff7f/sdks/typescript/packages/core/src/event-factories.ts) `buildEvent` | 换来早期失败；但迫使该模块不能进主入口，否则 zod 从可选变必装 |
| zod 作为可选 peer 依赖，用打包产物检查守住边界 | 同文件头注释 + `main-entry-zod-free.test.ts` 的描述 | 约束是“结构性”的（三层深再导出也能抓到），但需要测试基建持续维护 |
| `RUN_FINISHED.outcome` 可选 | 同文件 `createRunFinishedEvent` 注释 | 保住 legacy 生产者；消费方必须处理 `undefined` 分支 |
| `cancelled` 不接受 `result`，但允许 `usage` | 同文件 `createRunFinishedCancelledEvent` 注释 | 类型层面表达“取消无返回值”，减少误用 |
| 协议版本严格两段数字语法，非法值按“更新”警告 | [agent.ts](https://github.com/ag-ui-protocol/ag-ui/blob/7e7c1109f26e77cc32d87d351fb9e0b0bf56ff7f/sdks/typescript/packages/client/src/agent/agent.ts) `compareDeclaredProtocol` 注释 | 避免 `compare-versions` 的宽松解析掩盖协议不兼容 |
| `maxVersion` 更名为 `maxProtocolVersion` 并保留弃用别名 | 同文件 getter 注释 | 语义更准确（“对端上限”而非“本端实现”），迁移期需双 getter 解析逻辑 |
| `threadId` 懒生成 | 同文件 `threadId` getter 注释（引用 #3197） | 为兼容 workerd 的全局作用域限制，牺牲“构造即确定”的直觉 |
| `runInputs` 用模块级 WeakSet 而非实例字段 | 同文件顶部注释 | 因 `clone()` 不执行字段初始化器；代价是隐式全局状态 |
| `middlewares` 声明为 `protected` | 同文件字段注释 | 让自行实现 `clone()` 的子类（注释点名 `MastraAgent.clone()`）能携带中间件 |
| 构造期强校验 `maxProtocolVersion` | 同文件 `resolvedCeilingDuringConstruction` | 把类字段初始化顺序这类“运行时玄学”提前变成明确报错 |

## 6. 分步学习路径

**第 0 步：确认边界。** 读 [README.md](https://github.com/ag-ui-protocol/ag-ui/blob/7e7c1109f26e77cc32d87d351fb9e0b0bf56ff7f/README.md) 的 “What is AG-UI?” 与协议栈图说明，记下“事件 + 少量输入 + 传输无关中间件 + 参考 HTTP 实现”四件事。

**第 1 步：读规范而非 SDK。** 索引显示存在 `spec/` 目录（本文未读）。先弄清事件序列的规范性约束（尤其 chunk 的“续接”规则、`role` 缺省为 assistant、`timestamp` 单位不设规范），再回来看 SDK 如何实现。

**第 2 步：事件类型清单。** 以 [generated/events.ts](https://github.com/ag-ui-protocol/ag-ui/blob/7e7c1109f26e77cc32d87d351fb9e0b0bf56ff7f/sdks/typescript/packages/proto/src/generated/events.ts) 的 `EventType` 为权威列表，按 文本 / 工具 / 状态 / 运行生命周期 / 步骤 / 子 Agent / reasoning / activity 分组，逐组读接口注释。

**第 3 步：构造侧。** 读 [event-factories.ts](https://github.com/ag-ui-protocol/ag-ui/blob/7e7c1109f26e77cc32d87d351fb9e0b0bf56ff7f/sdks/typescript/packages/core/src/event-factories.ts)，重点看 `buildEvent` 与三个 `RUN_FINISHED` 便捷函数；再打开 `generated/schemas.ts`（**本文未读**）确认每个 schema 的必填/可选字段与范围约束。

**第 4 步：消费侧。** 读 [agent.ts](https://github.com/ag-ui-protocol/ag-ui/blob/7e7c1109f26e77cc32d87d351fb9e0b0bf56ff7f/sdks/typescript/packages/client/src/agent/agent.ts) 全文（本文只读到构造函数前），定位 `runAgent`、`connectAgent`、`onInitialize`、`clone` 的真实实现，验证第 4.2 节的管道顺序。

**第 5 步：横切模块。** 依次读 `@/verify`、`@/chunks`、`@/enforce`、`@/apply/default`、`@/middleware/compatibility-boundary`、`@/legacy/convert`、`./subscriber`。这些是理解“宽松格式匹配”“向后兼容”“订阅者状态变更合并”的关键，本文仅有导入线索。

**第 6 步：跨语言对照。** README 列出 Kotlin / Golang / Dart 等社区 SDK 及其文档路径（[README.md](https://github.com/ag-ui-protocol/ag-ui/blob/7e7c1109f26e77cc32d87d351fb9e0b0bf56ff7f/README.md)），可用于对照同一事件语义在不同语言中的落地。

## 7. 动手实验（设计，**均未执行**）

以下步骤用于验证本文的推断；执行前需自行准备环境，结果需自行记录。

1. **工厂校验边界**：用 `createTextMessageContentEvent({ messageId, delta: "" })` 与缺 `messageId` 的调用对比，观察是否抛错；再传多余字段，确认 zod 是 strip 还是 strict。预期依据：`buildEvent` 走 `schema.parse`；实际行为取决于 `generated/schemas.ts`（未读）。
2. **三种 RUN_FINISHED 对比**：分别调用 `createRunFinishedSuccessEvent({ pendingToolCallIds: [...] })`、`createRunFinishedInterruptEvent({ interrupts: [...] })`、`createRunFinishedCancelledEvent({...})`，打印产物，核对 `outcome` 形状与 `result` 是否被接受。预期依据：[event-factories.ts](https://github.com/ag-ui-protocol/ag-ui/blob/7e7c1109f26e77cc32d87d351fb9e0b0bf56ff7f/sdks/typescript/packages/core/src/event-factories.ts) 中三个函数的签名与注释。
3. **版本比较纯函数**：对 `compareDeclaredProtocol` 输入 `"1.0"`、`"1"`、`"1.0.0"`、`"1.x"`、`"2.0"`，核对返回是否为 `not-newer` / `uninterpretable` / `uninterpretable` / `newer`（相对 `PROTOCOL_VERSION`）。这是纯函数，可直接单测。
4. **构造期 ceiling 防御**：定义一个子类，让 `maxProtocolVersion` getter 读取一个在 `super()` 之后才初始化的实例字段，实例化时应抛 `AGUIError`。预期依据：`resolvedCeilingDuringConstruction` 的注释与实现。
5. **zod 边界复现**：按注释描述，把 `src/index.ts` 打包、zod 标为 external，检查产物是否残留 `zod` 导入；再人为加一条从 index 到 event-factories 的再导出，确认能被检出。这是对 `main-entry-zod-free.test.ts` 思路的复现，不是对它的运行。
6. **chunk 转换**：构造一段只含 `TEXT_MESSAGE_CHUNK` 的流，经 `transformChunks`（未读）后观察是否展开为 start/content/end 序列。
