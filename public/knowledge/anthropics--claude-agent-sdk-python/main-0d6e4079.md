## 1. 项目定位

**一句话**：这是一个「薄壳」SDK——它本身不实现 agent loop，而是用 Python 驱动一个随包捆绑的 Claude Code CLI 子进程，把 Python 侧的工具、hook、权限回调注入进去。

支撑证据：

1. README 说明安装后 **Claude Code CLI 自动捆绑，无需单独安装**，并可用 `ClaudeAgentOptions(cli_path="/path/to/claude")` 指向系统安装或指定版本（[README.md](https://github.com/anthropics/claude-agent-sdk-python/blob/2d485201617258867dd0f74b9e7307056f5938fe/README.md)）。
2. `pyproject.toml` 的 `description` 是 `"Python SDK for Claude Code"`，包名 `claude-agent-sdk`，版本 `0.2.174`，`requires-python = ">=3.10"`，构建后端起 `hatchling`，wheel 只含 `src/claude_agent_sdk`（[pyproject.toml](https://github.com/anthropics/claude-agent-sdk-python/blob/2d485201617258867dd0f74b9e7307056f5938fe/pyproject.toml)）。
3. 运行时直接依赖只有 5 个：`anyio`、`sniffio`、`mcp>=1.23.0,<3.0.0`、`jsonschema`、以及 3.10 下的 `typing_extensions`。**没有任何模型调用 SDK 依赖**（无 `anthropic`、无 `httpx`）——这从依赖表可直接看出，进一步印证「模型调用发生在 CLI 子进程内」这一判断（该因果解释属**推断**）。
4. 两个公开入口在 README 中被并列对比：`query()`（一次性、无状态）与 `ClaudeSDKClient`（双向、有状态）；后者「additionally enables **custom tools** and **hooks**」（[README.md](https://github.com/anthropics/claude-agent-sdk-python/blob/2d485201617258867dd0f74b9e7307056f5938fe/README.md)）。`__init__.py` 同时导出两者：`from .client import ClaudeSDKClient`、`from .query import query`（[__init__.py](https://github.com/anthropics/claude-agent-sdk-python/blob/2d485201617258867dd0f74b9e7307056f5938fe/src/claude_agent_sdk/__init__.py)）。

## 2. 基于已读代码的架构

### 2.1 分层（只写已被代码证实的层）

```
公共 API 面        __init__.py  →  query / ClaudeSDKClient / @tool / 类型 / 错误 / session API
                   │
顶层客户端         client.py       ClaudeSDKClient（有状态、双向、支持 custom tools + hooks）
内部执行器         _internal/client.py  InternalClient.process_query（一次性执行骨架）
                   │
控制协议           _internal/query.py   Query   ← 文件未读，仅见调用点
消息解析           _internal/message_parser.py parse_message  ← 未读，仅见调用点
                   │
传输抽象           _internal/transport.Transport（自定义实现可注入）
默认实现           _internal/transport/subprocess_cli.SubprocessCLITransport
```

**可见证据**：
- `client.py` 在 `__init__(self, options, transport: Transport | None = None)` 中接受自定义传输，docstring 明确「when provided it is used instead of the default subprocess transport」（[client.py](https://github.com/anthropics/claude-agent-sdk-python/blob/2d485201617258867dd0f74b9e7307056f5938fe/src/claude_agent_sdk/client.py)）。
- `_internal/client.py` 的 `process_query(..., transport: Transport | None = None)` 同样在 `transport is None` 时才构造 `SubprocessCLITransport`（[_internal/client.py](https://github.com/anthropics/claude-agent-sdk-python/blob/2d485201617258867dd0f74b9e7307056f5938fe/src/claude_agent_sdk/_internal/client.py)）。
- `__init__.py` 把 `Transport` 作为公共类型导出：`from ._internal.transport import Transport`（[__init__.py](https://github.com/anthropics/claude-agent-sdk-python/blob/2d485201617258867dd0f74b9e7307056f5938fe/src/claude_agent_sdk/__init__.py)）。**推断**：`Transport` 是被官方认可的扩展点，而非纯内部细节。

### 2.2 两个入口共享同一套「装配清单」

`ClaudeSDKClient._connect_inner` 与 `InternalClient._process_query_inner` 的装配步骤几乎逐条对应（这是本次读取中最强的结构性证据）：

| 装配步骤 | `client.py::_connect_inner` | `_internal/client.py::_process_query_inner` |
| --- | --- | --- |
| 权限配置 | `_configure_can_use_tool(self.options)` | `_configure_can_use_tool(options)` |
| 恢复会话覆盖 | `apply_materialized_options` | 同名调用 |
| 传输选择 | 自定义或 `SubprocessCLITransport` | 同 |
| SDK MCP 提取 | 遍历 `mcp_servers`，取 `config["type"] == "sdk"` 的 `config["instance"]` | 同 |
| 初始化超时 | `CLAUDE_CODE_STREAM_CLOSE_TIMEOUT` → `max(ms/1000, 60.0)` | 同，且注释写明「Match ClaudeSDKClient.connect()」 |
| 系统提示元数据 | 从 `system_prompt` dict 提取 `exclude_dynamic_sections` / `snapshot` | 同 |
| agents 序列化 | `asdict(agent_def)` 过滤 `None` | 同 |
| Query 构造 | `is_streaming_mode=True` + 12 个同名参数 | 同 |
| 会话镜像 | `set_transcript_mirror_batcher(build_mirror_batcher(...))` | 同 |

来源：[client.py](https://github.com/anthropics/claude-agent-sdk-python/blob/2d485201617258867dd0f74b9e7307056f5938fe/src/claude_agent_sdk/client.py)、[_internal/client.py](https://github.com/anthropics/claude-agent-sdk-python/blob/2d485201617258867dd0f74b9e7307056f5938fe/src/claude_agent_sdk/_internal/client.py)。

**取舍含义**：代码库选择了「复制装配逻辑」而不是「抽公共工厂函数」。好处是两个入口可以各自演进（例如 `connect()` 需要把 `_verbatim_prompts` 存到实例上，供整段会话中每条 prompt 使用；`process_query` 不需要）；代价是两者必须靠注释同步，源码里也确实留下了「Match ClaudeSDKClient.connect()」这类维护性注释。这是**观察 + 推断**，重构动机本身未在源码中说明。

### 2.3 一个可见的差异（阅读时必须自己确认）

构造传输时的 prompt 处理不同：

- `ClaudeSDKClient.connect()`：字符串 prompt **不**进传输，改为 `_empty_stream()`；注释说明 string prompt 稍后由 `transport.write()` 写入（[client.py](https://github.com/anthropics/claude-agent-sdk-python/blob/2d485201617258867dd0f74b9e7307056f5938fe/src/claude_agent_sdk/client.py)）。
- `InternalClient._process_query_inner()`：直接把原始 `prompt`（可能是 `str`）传给 `SubprocessCLITransport(prompt=prompt, ...)`，随后在 `isinstance(prompt, str)` 分支里又手动 `transport.write(...)`（[_internal/client.py](https://github.com/anthropics/claude-agent-sdk-python/blob/2d485201617258867dd0f74b9e7307056f5938fe/src/claude_agent_sdk/_internal/client.py)）。

两处对 `str` 的处理方式字面上不一致。`SubprocessCLITransport` 未读，无法判断它是否对 `str` 输入有特殊处理，因此**此处不下结论**，只标记为精读时的第一优先核验点（见 §6 实验 E2）。

### 2.4 权限与 hook 的注入路径

可见的入口参数（`Query.__init__` 的实参列表，两个客户端一致）：

```
transport, is_streaming_mode=True,
can_use_tool=...,                       ← 用户 Python 回调
hooks=_hooks_to_internal_format(...),   ← 用户 HookMatcher 列表转内部格式
sdk_mcp_servers=...,                    ← 进程内 MCP 工具实例
initialize_timeout=...,
agents=..., exclude_dynamic_sections=..., system_prompt_snapshot=...,
skills=..., forward_subagent_text=..., verbatim_prompts=...,
run_end_ceiling_ms=run_end_ceiling_ms(options.env),
```

来源：[_internal/client.py](https://github.com/anthropics/claude-agent-sdk-python/blob/2d485201617258867dd0f74b9e7307056f5938fe/src/claude_agent_sdk/_internal/client.py)。

README 明确了 `allowed_tools` 的真实语义，这一点很容易被误读，值得单独记住：

> `allowed_tools` is a permission allowlist: listed tools are auto-approved, and unlisted tools fall through to `permission_mode` and `can_use_tool` for a decision. **It does not remove tools from Claude's toolset.** To block specific tools, use `disallowed_tools`.

（[README.md](https://github.com/anthropics/claude-agent-sdk-python/blob/2d485201617258867dd0f74b9e7307056f5938fe/README.md)）

也就是说权限是**三层叠加**：`allowed_tools`（预批准）→ `permission_mode` → `can_use_tool` 回调 → hook 的 `permissionDecision`。README 给的 hook 示例返回 `{"hookSpecificOutput": {"hookEventName": "PreToolUse", "permissionDecision": "deny", ...}}` 来阻断 `./foo.sh`，并配合 `HookMatcher(matcher="Bash", hooks=[...])` 只匹配 Bash（同上）。`_configure_can_use_tool` / `_hooks_to_internal_format` 的**实现未读**，它们具体做校验还是转换属**推断**（名称 + 调用位置）。

### 2.5 会话存储：可插拔 + 双后端 API

`__init__.py` 的导出列表显示 session 相关能力成对出现：

- 本地：`list_sessions`、`get_session_info`、`get_session_messages`、`get_subagent_messages`、`list_subagents`、`fork_session`、`delete_session`、`rename_session`、`tag_session`
- 对应 store 版本：`*_from_store` / `*_via_store`
- 另有 `import_session_to_store`、`InMemorySessionStore`、`project_key_for_directory`、`fold_session_summary`

（[__init__.py](https://github.com/anthropics/claude-agent-sdk-python/blob/2d485201617258867dd0f74b9e7307056f5938fe/src/claude_agent_sdk/__init__.py)）

`pyproject.toml` 的 `[project.optional-dependencies].examples` 注释进一步指出 `examples/session_stores/` 下有「SessionStore reference adapters」，其后端依赖是 `boto3`/`moto[s3]`、`redis`/`fakeredis`、`asyncpg`——即 S3、Redis、Postgres 三类参考实现（**这些适配器文件未读取**，结论只来自 pyproject 注释与依赖名，属**推断**）。

运行时链路里能看到 store 的两个介入点：

1. **恢复**：`materialize_resume_session(options)` 把 store 里的会话落地到临时 `CLAUDE_CONFIG_DIR`（源码注释：写入 `.credentials.json` 副本），再由 `apply_materialized_options` 覆盖 `resume/continue/env`（[client.py](https://github.com/anthropics/claude-agent-sdk-python/blob/2d485201617258867dd0f74b9e7307056f5938fe/src/claude_agent_sdk/client.py)）。
2. **镜像**：`build_mirror_batcher(store=..., materialized=..., env=..., on_error=..., flush_mode=options.session_store_flush)` 挂到 `Query` 上，写入失败经 `_on_mirror_error` 回传 `query.report_mirror_error`（两个客户端都有这段）。

### 2.6 可选的 OpenTelemetry

`pyproject.toml` 里 `opentelemetry-api` 只在 `[project.optional-dependencies].otel` 中；mypy override 注释说明 `subprocess_cli.py` 里的 import「is guarded by try/except ImportError」（[pyproject.toml](https://github.com/anthropics/claude-agent-sdk-python/blob/2d485201617258867dd0f74b9e7307056f5938fe/pyproject.toml)）。**推断**：遥测在传输层（`subprocess_cli.py`）实现且为软依赖；该文件未读。

## 3. 关键调用链

### 3.1 链 A：一次性查询（`query()` → InternalClient）

```
query(prompt, options)                       ← query.py 未读，函数体未知
  └─> InternalClient.process_query(prompt, options, transport=None)     [可见]
        ├─ validate_session_store_options(options)                      [可见]
        ├─ materialized = await materialize_resume_session(options)      [transport is None 时]
        ├─ inner = self._process_query_inner(...)
        ├─ async for msg in inner: yield msg
        └─ finally: await inner.aclose(); await materialized.cleanup()
```

`_process_query_inner` 内部（完整可见）：

```
_configure_can_use_tool(options) → apply_materialized_options(...)
→ SubprocessCLITransport(prompt, options) → await transport.connect()
→ 提取 sdk_mcp_servers / system_prompt 标志 / agents_dict / initialize_timeout
→ Query(transport, is_streaming_mode=True, can_use_tool, hooks, sdk_mcp_servers, ...)
→ [若 session_store] set_transcript_mirror_batcher(build_mirror_batcher(...))
→ await query.start();  await query.initialize()
→ if str:  构造 user_message dict → stamp_user_message(...) → JSON + "\n" → transport.write
           query.spawn_task(query.wait_for_result_and_end_input())
   if AsyncIterable: query.spawn_task(query.stream_input(prompt))
→ async for data in query.receive_messages(): parse_message(data) → 非 None 则 yield
→ finally: await query.close(); query.close_receive_stream()
```

来源：[_internal/client.py](https://github.com/anthropics/claude-agent-sdk-python/blob/2d485201617258867dd0f74b9e7307056f5938fe/src/claude_agent_sdk/_internal/client.py)。

**`query()` 到 `InternalClient` 的这一跳是推断**：`query.py` 未读。依据是 README 指明 `query()` 定义在 `src/claude_agent_sdk/query.py`、`__init__.py` 中 `from .query import query`、以及 `_internal/client.py` 提供了一个签名匹配的 `process_query`。

链 A 中可直接读出的协议事实：写入 stdin 的 user 消息形状是

```python
{"type": "user", "session_id": "", "message": {"role": "user", "content": prompt},
 "parent_tool_use_id": None}
```

经 `stamp_user_message(user_message, configured_options.verbatim_prompts)` 加工后 `json.dumps(...) + "\n"`。即 **NDJSON 行协议**（推断自 `+"\n"` 的分帧方式）。

### 3.2 链 B：交互式会话（`ClaudeSDKClient.connect`）

```
connect(prompt=None)                                          [可见]
  ├─ actual_prompt = prompt if isinstance(prompt, AsyncIterable) else _empty_stream()
  ├─ validate_session_store_options(self.options)
  ├─ self._materialized = await materialize_resume_session(self.options)
  │                       if self._custom_transport is None else None
  ├─ try: await self._connect_inner(prompt, actual_prompt)
  └─ except BaseException: await self.disconnect(); raise
```

`_connect_inner` 完成 §2.2 表中的全部装配，创建 `self._query = Query(...)` 后（**源码在此截断**）——**推断**：后续应是 `query.start()` / `query.initialize()` / prompt 写入，与链 A 平行；依据是 `Query(...)` 的实参完全一致，且内部客户端留有「Match ClaudeSDKClient.connect()」注释。

`connect` 的异常处理注释给出了一条重要的资源顺序约束：**先 `disconnect()`（关子进程/读任务），再删除临时 `CLAUDE_CONFIG_DIR`**，否则子进程可能正在读写被删目录。

来源：[client.py](https://github.com/anthropics/claude-agent-sdk-python/blob/2d485201617258867dd0f74b9e7307056f5938fe/src/claude_agent_sdk/client.py)。

同一约束在 `InternalClient.process_query` 的 `finally` 里以更显式的方式实现，并附了 PEP 533 的理由：

```python
# ``async for`` does NOT close its iterator when the loop body raises
# (PEP 533 was deferred). Explicitly aclose the inner generator first ...
try:
    await inner.aclose()
finally:
    if materialized is not None:
        await materialized.cleanup()
```

### 3.3 链 C：进程内自定义工具

```
@tool("greet", "Greet a user", {"name": str})   → SdkMcpTool(name, description, input_schema, handler, annotations)
create_sdk_mcp_server(name=..., version=..., tools=[...])   ← README 使用，定义未读
ClaudeAgentOptions(mcp_servers={"tools": server}, allowed_tools=["mcp__tools__greet"])
  └─> 客户端遍历 mcp_servers，命中 config["type"] == "sdk" → sdk_mcp_servers[name] = config["instance"]
      └─> Query(sdk_mcp_servers=...) 交给控制协议
```

`SdkMcpTool` 的字段在 `__init__.py` 中可见；`tool()` 装饰器的返回值类型标注也是 `Callable[..., SdkMcpTool[Any]]`。`create_sdk_mcp_server` 与 `McpSdkServerConfig` 只出现在 README 与类型导出列表中，**实现未读**。工具名在模型侧带 `mcp__<server>__<tool>` 前缀（README 示例 `allowed_tools=["mcp__tools__greet"]`）。

## 4. 设计取舍（每条都对应可见证据）

| 取舍 | 源码证据 | 我的解读 |
| --- | --- | --- |
| **不自研 agent loop，包 CLI** | 依赖表无模型 SDK；README 称 CLI 随包捆绑、可 `cli_path` 覆盖 | 用子进程换取「SDK 与 CLI 行为一致」；代价是进程边界带来的序列化与生命周期管理（见 §3.2 的临时目录排序约束） |
| **传输层可替换** | `transport` 参数在两个客户端都存在；`Transport` 从 `__init__.py` 导出 | 测试/嵌入场景可注入假传输；docstring 也明确「CLI-flag options 不作用于自定义传输」 |
| **运行时无关（anyio）** | 依赖 `anyio` + `sniffio`；README 用 `anyio.run`；pytest `-p anyio`；dev extra 有 `anyio[trio]` | 同一份代码可跑 asyncio 与 trio |
| **有状态客户端限定在同一 async context** | `ClaudeSDKClient` docstring 的 Caveat：内部维持持久 anyio task group，从 `connect()` 到 `disconnect()`，跨不同 trio nursery / asyncio task group 使用不被支持，且注释自认「Ideally, this limitation should not exist」 | 明确承认的架构债，值得作为阅读时的「为什么」锚点 |
| **装配逻辑复制而非抽象** | §2.2 对比表 | 换取两入口独立演进；成本是同步注释 |
| **权限用「白名单=预批准」而非「白名单=可见集」** | README 显式警告 + 指向 `disallowed_tools` | 避免用户误以为 `allowed_tools` 是沙箱；真正的收窄要靠 `disallowed_tools` / `can_use_tool` / hook deny |
| **跨 mcp 大版本兼容层** | 依赖 `mcp>=1.23.0,<3.0.0`；`ToolAnnotations` 同时接受 camelCase 与 snake_case，`_HINT_WIRE_NAMES` 折叠到 wire 名，且 docstring 说明 1.x 属性访问是 `.readOnlyHint`、2.x 是 `.read_only_hint` | 用 `extra="allow"` + `__init__` 归一化，把版本差异挡在 SDK 边界内 |
| **Claude Code 私有 hint 混杂在 MCP 注解里** | `maxResultSizeChars` 字段 + docstring：「not an MCP hint but a Claude Code one」，经 `_meta` 传给 CLI | 有意为之的实用主义，文档里写清了边界 |
| **可观测性可选** | `otel` extra + `subprocess_cli.py` 的 `try/except ImportError`（pyproject 注释） | 零硬依赖换可选追踪 |
| **恢复态必须落地到临时目录** | `materialize_resume_session` 写 `.credentials.json` 副本；`apply_materialized_options` 覆盖 `resume/continue/env`；自定义 transport 时**跳过**该步骤（两次 `if transport is None`） | 凭据不进入自定义传输路径，是刻意的短路 |
| **未知消息类型静默丢弃** | `parse_message(data)` 返回 `None` 时 `if message is not None` 才 yield | 前向兼容：新版 CLI 多发的消息类型不会打断老 SDK |
| **初始化超时下限 60s** | `max(initialize_timeout_ms / 1000.0, 60.0)`，默认 `60000` | 默认值恰等于下限，环境变量只能调高不能调低 |
| **严格类型与工程约束** | mypy `strict = true` + 多项 `disallow_*`；ruff 选定 E/W/F/I/N/UP/B/C4/PTH/SIM；py310 目标 | `PTH`（强制 pathlib）与 `PTH`/`SIM` 这类规则说明风格上偏防御 |
| **sdist 必须带 `/scripts`** | sdist include 注释：`tests/test_build_wheel.py` 等在 import 时从 `scripts/` 加载被测对象，缺 `/scripts` 连测试都收集不了 | 测试与构建脚本耦合，是被记录下来的历史约束（`scripts/build_wheel.py`、`download_cli.py`、`update_cli_version.py` 均由注释提及，文件未读） |

## 6. 动手实验（设计，**尚未执行**）

> 以下都未运行，仅是基于已读代码的验证方案。执行前请自行确认环境。

**E1 — 验证 `query()` 的委托关系**（检验 §3.1 的推断）
在 `InternalClient.process_query` 的 `async for msg in inner` 处加日志，跑 README 的 Quick Start。若日志出现，则推断成立；若没有，说明 `query()` 走了别的路径。

**E2 — 核对 `str` prompt 的实际写入次数**（§2.3）
在 `SubprocessCLITransport` 的构造与 `write()` 上分别埋点，对比 `query()` 与 `ClaudeSDKClient.connect(prompt="...")` 两条路径。预期：`connect` 路径下传输不拿到字符串 prompt。若 `SubprocessCLITransport` 对 `str` 有特殊处理，`process_query` 就可能出现重复写入——这正是需要确认的点。

**E3 — 验证初始化超时的下限**
`initialize_timeout = max(int(env)/1000.0, 60.0)`。静态推论：设 `CLAUDE_CODE_STREAM_CLOSE_TIMEOUT=1000` 实际仍是 60s；设 `120000` 才是 120s。可通过日志打印 `initialize_timeout` 验证（不必真的等 60 秒）。

**E4 — 验证取消时的关闭顺序**（§3.2）
在 `async for message in query(...)` 的循环体内主动 `raise`，观察日志顺序是否为 `query.close()` → `materialized.cleanup()`，以及临时 `CLAUDE_CONFIG_DIR` 是否被删除。这是对 PEP 533 注释的直接检验。

**E5 — 验证未知消息类型被跳过**
让 `parse_message` 接收一个伪造的未知 `type`，确认返回 `None` 而非抛异常（断言点在 `_process_query_inner` 的 `if message is not None`）。

**E6 — 验证 `allowed_tools` 不是收敛工具集**
按 README 只写 `allowed_tools=["Read"]`，让模型做一次需要 Bash 的动作。按 README 的语义，Bash 仍应可用（只是需要走 `permission_mode` / `can_use_tool`）。用 `disallowed_tools=["Bash"]` 做对照组。

**E7 — hook deny 的短路点**
复现 README 的 `check_bash_command`，观察 `./foo.sh` 被拒时消息流里出现什么（`permissionDecision` 是否作为 tool 结果回到模型）。

**E8 — 自定义传输下的 store 短路**
传 `transport=...` + 配置 `session_store`，确认 `materialize_resume_session` 从未被调用（`if transport is None` 的分支）。可用 monkeypatch 计数。

### 附：一句话复述

这个 SDK 的本体是**一个装了 12 个旋钮的 `Query` 装配器**——传输、权限、hook、进程内工具、会话镜像都在 `Query(...)` 的构造参数里；`ClaudeSDKClient` 与 `InternalClient` 是同一份装配清单的两个使用者，区别只在「一条 prompt 就结束」还是「同一上下文里反复发」。真正难的部分（控制协议、CLI 子进程、schema 校验、会话落地）全部在本文未覆盖的那几个文件里。
