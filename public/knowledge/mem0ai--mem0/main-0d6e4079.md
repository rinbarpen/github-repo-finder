## 1. 项目定位

- 定位陈述（README 原文）："The Memory Layer for AI Agents - Drop-in memory infrastructure for AI agents and apps."，即给 AI 应用提供**持久化记忆、检索与个性化上下文**（[README.md](https://github.com/mem0ai/mem0/blob/26cdefb46600c0fa5953c4b5ee5003c125539fc4/README.md)）。
- 三种交付形态在 README 中并列：**Library（pip/npm）**、**Self-Hosted Server（docker compose）**、**Cloud Platform（托管 API）**（同上）。
- README 声明的能力：多级记忆（User / Session / Agent）、混合检索（语义 + BM25 + 实体）、时间推理、实体链接；并声明 "**Single-pass ADD-only extraction** -- one LLM call, no UPDATE/DELETE"（同上）。这条声明与源码中导入的 `ADDITIVE_EXTRACTION_PROMPT` 名称方向一致（[mem0/memory/main.py](https://github.com/mem0ai/mem0/blob/26cdefb46600c0fa5953c4b5ee5003c125539fc4/mem0/memory/main.py)），但**具体抽取流程未在片段中读到**。
- 依赖面显示这是"薄核心 + 大量可选后端"：核心依赖仅 `qdrant-client`、`pydantic`、`openai`、`httpx`、`posthog`、`pytz`、`sqlalchemy`、`protobuf`；向量库/LLM 各自是 optional extra（`vector-stores`、`llms`、`extras`、`nlp` 等）（[pyproject.toml](https://github.com/mem0ai/mem0/blob/26cdefb46600c0fa5953c4b5ee5003c125539fc4/pyproject.toml)）。构建用 `hatchling`，wheel 只打包 `mem0` 包。

**读它的理由（与证据索引一致）**：一次记忆写入与一次检索，就能串起"输入校验 → 身份边界 → LLM 抽取 → 向量库 + 历史库 → 结果整形"的完整链路。

## 3. 关键调用链

### 3.1 托管链路：`MemoryClient` → HTTP API

```
业务代码
  └─ MemoryClient(api_key=…, host=…)
       ├─ api_key 缺失 → ValueError("Mem0 API Key not provided…")
       ├─ user_id = md5(api_key)
       ├─ 复用外部 httpx.Client 时：base_url 覆盖 + _apply_client_headers()
       └─ 否则新建 httpx.Client(base_url=self.host, headers=…)
```
证据：[mem0/client/main.py](https://github.com/mem0ai/mem0/blob/26cdefb46600c0fa5953c4b5ee5003c125539fc4/mem0/client/main.py)（片段在 `httpx.Client(base_url=self.hos` 处截断，**构造函数后半段未读到**）。

值得注意的契约细节（均在片段内可见，同链接）：
- 头部三类语义：`X-Mem0-Source` / `X-Application` 是 **set-once**（外层已设置则 SDK 让位），`X-Mem0-Client` 是 **append-only**（`_client_headers` + `_client_stack` + `_bounded_stack`，上限 `MAX_STACK_ENTRIES=4`、`MAX_STACK_CHARS=200`，且"预留槽位是自己的"，超出时整条丢弃而非截断字符）。
- 身份参数**必须走 filters，不能顶层传**：`ENTITY_PARAMS = {user_id, agent_id, app_id, run_id}`（注意比 OSS 侧多 `app_id`、少 `run_id` 之外的差异见 4.2），`_reject_filters` 反向禁止向"读顶层 ID"的端点传 filters。
- 空/纯空白实体 ID 直接 `ValueError`，理由写在错误信息里："an empty ID would match every memory in the project"，并提示"真要删全部请显式 `delete_all()` 传 `'*'`"。
- `_encode_path_segment` 用 `quote(str(value), safe="")` 做路径段转义；`_sdk_version()` 刻意在函数内 `importlib.metadata.version("mem0ai")`，注释说明"从包根导入会循环依赖"。
- 遥测：`setup_config()` 在模块导入期执行；`_maybe_alias_anon_to_email` 明确 best-effort、"never raises"，并用 `aliased_pairs` 做幂等标记。

**未读**：`add` / `search` / `get_all` / `delete` / `delete_all` / `update` / profiles 等具体方法体，因片段截断。

### 3.2 本地链路：`Memory` 的写入/检索骨架

片段内可确认的**入口守卫**（[mem0/memory/main.py](https://github.com/mem0ai/mem0/blob/26cdefb46600c0fa5953c4b5ee5003c125539fc4/mem0/memory/main.py)）：

1. `_reject_top_level_entity_params(kwargs, "…")` —— 顶层出现 `user_id/agent_id/run_id` 直接报错，提示改用 `filters={'user_id': '...'}`。
2. `_validate_and_trim_entity_id(value, name)` —— 非 str 先 `str()` 强转（注释：调用方常传数据库整型主键，在此单点归一），去首尾空白，拒绝空串，**拒绝任何内部空白**。
3. `_validate_search_params(threshold, top_k)` —— `threshold ∈ [0,1]`，`top_k` 必须是非负 int 且排除 bool。
4. `_validate_and_trim_search_query(query)` —— 非 str / 空白串即报错。
5. `_strip_identity_keys(metadata, existing_payload, context=…)` —— 把身份键从**调用方 metadata** 中剥离；更新路径上"重发相同值静默放行，只在值变化时 warn"，创建路径传空 dict 即全部剥离并 warn。注释直接引用 issue 号 `#4490, #6277, #6655`。
6. `_safe_deepcopy_config(config)` —— 先 `deepcopy`，失败则按 `model_dump()` / `__dict__` 克隆，并做**分层字段处理**：`_RUNTIME_FIELDS`（`http_auth`、`auth`、`connection_class`、`ssl_context`）保留原对象；命中 `_SENSITIVE_FIELDS_EXACT` 或 `_SENSITIVE_SUFFIXES`（`_password/_secret/_token/_credential/_credentials`）的置 `None`；重建失败再退化为匿名类对象。
7. `DELETE_ALL_BATCH_SIZE = 1000`、`_vector_store_list_rows()`（兼容 `[[...]]` 嵌套返回）。

**推断（合理但未证实）**：上述函数是 `add/search/get_all/delete_all/update` 的公共前置，即为每条公开方法提供**统一的不变量**（身份只能经 filters、ID 必须规范、配置克隆不得泄漏密钥）。要证实需读这些方法体（本文未覆盖）。

### 3.3 代理链路：`Completions.create` 的读/写时序

```
create(model, messages, user_id/agent_id/run_id, filters, top_k, …)
 ├─ 三者全空 → ValueError("One of user_id, agent_id, run_id must be provided")
 ├─ litellm.supports_function_calling(model) 为假 → ValueError
 ├─ prepared_messages = _prepare_messages(messages)
 │    └─ 首条不是 system → 前插 {"role":"system","content":MEMORY_ANSWER_PROMPT}
 └─ if prepared_messages[-1]["role"] == "user":
      ├─ _async_add_to_memory(messages, …)        # 后台 daemon 线程写记忆
      ├─ relevant_memories = _fetch_relevant_memories(…)  # 同步读记忆
      │    └─ 取最后 6 条消息拼 "role: content"，"\n".join 作 query
      └─ prepared_messages[-1]["content"] = _format_query_with_memories(…)  # 就地改写
 └─ litellm.completion(…全部透传参数…)
 └─ 按 mem0_client 类型分别 capture_event / capture_client_event
```
证据：[mem0/proxy/main.py](https://github.com/mem0ai/mem0/blob/26cdefb46600c0fa5953c4b5ee5003c125539fc4/mem0/proxy/main.py)。

同一文件里可读到的**后端语义分叉**（明确证据）：

```python
if isinstance(self.mem0_client, mem0.memory.main.Memory):
    memories_text = "\n".join(m["memory"] for m in relevant_memories["results"])
    if relevant_memories.get("relations"): entities = [...]
elif isinstance(self.mem0_client, mem0.client.main.MemoryClient):
    memories_text = "\n".join(m["memory"] for m in relevant_memories)
```
即：**OSS `search` 返回带 `results`（及可选 `relations`）的字典；托管 `search` 返回列表**。这是两条 SDK 未做成同一返回契约的直接证据。

## 4. 设计取舍（逐条附证据）

### 4.1 头部身份：set-once vs append-only
外层包装器（插件、harness）的身份必须存活，SDK 只把自己"追加"进栈并**保留自己的槽位**；注释直言早期实现"先 append 再截到 4 条"会把 SDK 自己裁掉。取舍是**可观测性（谁在调用）优先于简洁**，代价是一段 200 字符/4 条的脆弱字符串协议。
证据：[mem0/client/main.py](https://github.com/mem0ai/mem0/blob/26cdefb46600c0fa5953c4b5ee5003c125539fc4/mem0/client/main.py)（`_bounded_stack`、`_client_headers`、`_apply_client_headers`）。

### 4.2 身份边界收口在两个"窄门"
- 托管侧：`filters` 与顶层 ID 互斥（`_reject_filters` / `_reject_blank_entity_ids`）。
- OSS 侧：顶层 ID 一律拒绝（`_reject_top_level_entity_params`），且 metadata 不得写入身份键（`_strip_identity_keys`）。
取舍：**把租户隔离做成参数校验问题，而不是文档约定**，用抛错 + warn 替代静默纠正。代价是两套 SDK 的参数习惯不一致：托管侧 `ENTITY_PARAMS` 含 `app_id`，OSS 侧含 `run_id` 而不含 `app_id`（对比两文件的同名常量）。
证据：[mem0/client/main.py](https://github.com/mem0ai/mem0/blob/26cdefb46600c0fa5953c4b5ee5003c125539fc4/mem0/client/main.py)、[mem0/memory/main.py](https://github.com/mem0ai/mem0/blob/26cdefb46600c0fa5953c4b5ee5003c125539fc4/mem0/memory/main.py)。

### 4.3 遥测"永不失败"
`_maybe_alias_anon_to_email` 整体 try/except 且注释写明 best-effort；telemetry 关闭时连标记都不写，以保证关/开切换仍幂等。取舍：**不因遥测影响主流程**。
证据：[mem0/client/main.py](https://github.com/mem0ai/mem0/blob/26cdefb46600c0fa5953c4b5ee5003c125539fc4/mem0/client/main.py)。

### 4.4 配置克隆的双目标冲突
`_safe_deepcopy_config` 同时要"保住不可序列化的运行时对象"与"抹掉密钥"，所以先 deepcopy，失败才回退并按字段分层处理。取舍：**可用性优先，但宁可把密钥置 None 也不外泄**。
证据：[mem0/memory/main.py](https://github.com/mem0ai/mem0/blob/26cdefb46600c0fa5953c4b5ee5003c125539fc4/mem0/memory/main.py)。

### 4.5 代理层：写异步、读同步
`_async_add_to_memory` 起 daemon 线程，`_fetch_relevant_memories` 同步等待；且 `_fetch_relevant_memories` 里留了 `# TODO: Make it better by summarizing the past conversation`，并把 query 硬限为最后 6 条消息。取舍：**首字延迟优先于记忆新鲜度**——本轮提问读不到本轮刚说的话。
证据：[mem0/proxy/main.py](https://github.com/mem0ai/mem0/blob/26cdefb46600c0fa5953c4b5ee5003c125539fc4/mem0/proxy/main.py)。

### 4.6 演进痕迹被写进注释
源码注释里保留了"上一版错在哪"（`_bounded_stack` 的注释、`_apply_client_headers` 的"blanket update() 是反例"）以及 issue 编号（`#4490, #6277, #6655`）。这是**把设计契约当文档维护**的取舍，读代码时价值很高。
证据：[mem0/client/main.py](https://github.com/mem0ai/mem0/blob/26cdefb46600c0fa5953c4b5ee5003c125539fc4/mem0/client/main.py)、[mem0/memory/main.py](https://github.com/mem0ai/mem0/blob/26cdefb46600c0fa5953c4b5ee5003c125539fc4/mem0/memory/main.py)。

## 6. 分步学习路径

**第 0 步｜定边界（15 分钟）**
